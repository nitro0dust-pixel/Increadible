- **`scripts/capacity.js` and `scripts/loadtest.js` could pick a port already in use.** They chose a random port in 20000-40000, which overlaps Linux's outgoing-connection range (32768-60999); on 2026-10-14 the server they started lost that race in CI (PR #68's first run: `scripts/capacity.js failed: Error: server exited: } |  | Node.js v24.21.0`, the tail of an uncaught `EADDRINUSE`; reproduced here by holding the port: the same tail). ### Added
- **Request drivers, stage 2 of 4: three deeper scenarios and the scenario format they needed** ([#75](https://github.com/nitro0dust-pixel/Increadible/pull/75); `docs/DRIVERS.md` sections 3.6, 5 and 6): `gateway` (discovery, one call to each of the nine APIs, the cache, every error the tools name, aggregation and its limit, the counters checked against the number of calls the scenario makes), `ab-statistics` (60 + 60 known measurements, the mean, standard deviation, interval, effect size, p-value and winner checked against arithmetic worked out from the values; the same data in both variants gives no winner) and `routing-rules` (the built-in rules, priority order, a disabled rule, lists, ties, refused rule sets that change nothing, no rules at all). ## [1.0.2] - 2026-10-09

### Fixed
- **`npm run mcpb` failed on Windows when Node is installed under a path with a space** (`C:\Program Files\nodejs`, the installer's default): `scripts/mcpb.js` started the compiler through `cmd.exe`, which split the path (`'C:\Program' is not recognized`). Found by the owner on 2026-10-09. Now only `npm.cmd` goes through a shell (Node requires one for a `.cmd` file); `node` starts directly. The package's content is unchanged (the same SHA-256). Verified by the owner on Windows: the fixed build wrote `increadible-1.0.2.mcpb` with SHA-256 `3594d5fd...`, identical to the Linux and CI builds. ([#38](https://github.com/nitro0dust-pixel/Increadible/pull/38))
- **The Claude Desktop package did not answer in the app (version 1.0.0; fixed in 1.0.1).** Seen on the owner's Windows machine: Claude Desktop's log showed `initialize` sent and never answered ("Request timed out", shown as "didn't respond within a minute"), its probe copies giving up after 4 s, and one closing during a `server/discover` probe. The app starts several copies of the server on one data folder and kills them at will. Opened at start-up, the A/B data file made a second copy crash on the lock, a lock left by a killed copy froze start-up for up to 17 s, and a retry loop on a stale lock that cannot be removed (Windows) had no deadline. The cause was not proven from here; every known suspect is removed: **`AB_LAZY_OPEN`** (new, off by default, set by the package) opens the A/B data on the first A/B tool call, so the handshake and the other tools never depend on the data folder, and a held or unusable file is the error of that one call (the next call tries again; a lock is never waited for inside a call); the lock loop now respects its deadline and sleeps between attempts; **`src/main.ts`**, the package's entry, always starts the server (`index.ts` starts itself only when it is the program); the data folder is no longer flushed on Windows (a directory handle cannot be); a one-line `ready on stdio` appears on stderr at start. **Behaviour of containers and the HTTP mode is unchanged** (the default still opens at start-up and refuses a second copy at once). - **API gateway resource bounds (audit findings GW-1, GW-3):** the result cache grew with every distinct call and never shrank (2 000 calls with 200 KB of params held 385 MB of heap, against a 256Mi pod limit), and one `aggregate_apis` request started every call at once (5 000 requested, 5 000 started together, which in live mode means 5 000 simultaneous calls to a provider with the gateway's own key).
